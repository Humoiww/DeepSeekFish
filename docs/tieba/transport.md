# 贴吧发布传输层

[贴吧目录](README.md) · [工具与回执](publishing.md) · [研究依据](research.md)

模型使用统一的 `publish_tieba`，不选择或拼接底层协议。账号会话、发言意图、传输与可见性核对分开处理。

## 当前通道

| 动作／配置 | 传输 |
| --- | --- |
| `reply`、`comment`，已有网页授权的账号 | 独立 Chromium 中官网原生控件和网站 JavaScript |
| `reply`、`comment`，未启用网页路径 | 已移植的 App Protobuf |
| `thread` 新主题 | 独立 Chromium 中官网原生发贴编辑器；`/c/c/thread/add_pc` |
| 小吧主申请 | 独立的官网申请表，见 [申请说明](moderator.md) |

已有网页路径不表示百度向项目授予通用自动化 API 权限。某次失败不触发另一个写通道补发。

## 官方网页新主题

从目标吧首页点击官网“发贴”，等待原生发布器加载，在 `#tb-editor-title` 和 `#tb-editor-content` 内通过正常输入填写，点击发布器的“发布”。依据已核对的官网 `publish.632c318a.js` 与 `index.513973fe.js`，由官网自己的 JavaScript 组装 FormData、取得验证信息并请求 `/c/c/thread/add_pc`；不复制令牌或重造 App 请求。提交检查匹配吧 ID、吧名、标题及正文，回执读取主题 TID，不能把首楼 PID 当主题链接。新主题不会降级到旧 App 通道。

只有主人明确授权再次提交某个旧请求时，内部一次性发布授权才可关联 `retryOf`；模型参数不开放此字段，旧回执保留。普通调用仍返回原来的未知／已接受送达结果，不自动重发。

## 官方网页回复

网页使用 `/c/c/post/add_pc`。浏览器按真实父楼 `pid` 定位页面，用父楼／子回复组件的实际 ID 找普通回复按钮，编辑框与发布按钮限定在选中的组件内。

当前核对过的官网脚本 `pb.160c8c07.js`：

- 普通新楼层不带父楼引用。
- 楼中楼的 `quote_id/repostid` 指向父楼。
- 回复某条子评论时另带 `sub_post_id`，官网添加 `回复 #(reply, portrait, name_show) :正文`。
- 编辑框只输入正文，出站内容核对包含官网产生的真实接收者前缀。
- 现有 `add_pc` 的 PID 和验证 `info` 可以位于响应根层，不能只读取 `data.pid`。

只观察正常界面绑定并操作控件，不直接设置 Vue 状态、不调用页面内部发布函数、不复制验证凭据。发送前保存意图，页面请求核对实际目标及内容。尚未点击提交的编辑器／目标准备错误记为 `notSubmitted`，不当作未知送达。

## App Protobuf 依据

协议来自 [dsh-tieba-dive 固定提交](https://github.com/Nekomeow114/dsh-tieba-dive/tree/06e1657eb5262d3d2337466debf0a7ca1c165fbf)的 `lib/tieba.js` 与 `CHANGELOG.md`。移植了 `encodeAddFloor`、`encodeAddPost`、`replyFloor/replySub` 对应结构和 `parseAddPostResponse`；许可见 [MIT 归属](../../third_party/dsh-tieba-dive.LICENSE)。没有引入上游的人格、心跳、账号管理或失败切换策略。

| 项目 | 实现 |
| --- | --- |
| 端点 | `/c/c/post/add?cmd=309731&format=protobuf` |
| 外层 | multipart `data` 文件部分；`x_bd_data_type: protobuf` |
| 消息 | 顶层字段1为 data，data 字段1为 common |
| common | 字段1=Android类型，2=`22.12.1.0`，10=BDUSS，11=TBS；data 字段4另带TBS |
| 正文与目标 | data 字段19/26/30/45 对应 content/fid/kw/tid，ID 保持字符串 |
| 普通回复 | `encodeAddFloor`，含上游固定字段及55=`13` |
| 楼中楼 | `encodeAddPost`，46=quote_id、49=repostid、50=sub_post_id、20=reply_uid |
| 显示名 | 58，从实际账号身份可取得时传入 |
| 回执 | 顶层1为错误，顶层2为 data，data 字段3为 PID 字符串 |

multipart 在内存构造，不把含凭据消息写成临时文件。响应支持 gzip/deflate/br，压缩体和解压输出分别有大小边界。私有凭据由隔离传输添加，不进入模型或普通日志。

以前的缺陷是把普通 URL-encoded 字段发往旧 `/c/c/post/add`，只尝试 JSON 响应；更换 URL 或 User-Agent 不能把它变成完整 Protobuf。当前编码与固定上游离线样本的核对是既有格式证据，不能代替平台接受或公开可见性。

## 回执和可靠性

网页与 App 最终都使用相同的发布记录和只读核对。接受、有效 ID、本人可见、公开可见、后来系统删除分别记录，详见 [发布说明](publishing.md)。解析异常、验证码及未知结果不自动重发。

App Protobuf 有单次成功证据，也遇过平台安全验证；网页原生回复有真实接受／公开可见样本。楼中楼的父楼定位、组件范围和前缀核对已修复，但本次文档整理没有新增真实发言，不能宣称所有子回复场景已通过端到端验收。平台验证与审核仍可能变化。

### 正文换行

`publish_tieba.content` 是纯文本，JSON 只解码一次，分段应传真正的换行。曾有模型把段落写成字面 `\n\n`，官网编辑器便原样输入。现在传输边界会将代码片段之外、连续的转义换行还原成段落换行，同时让网页编辑器与待发送字段使用同一份正文；单个转义示例和路径不做全局反转义。原始工具参数与历史回执保持原样，历史帖子不会自动修改或重发。

### 主人操作画面的生命周期

主人打开的官网发言画面，在提交、只读检查返回之后继续显示真实页面，包括本地校验失败、平台拒绝、已接受、未确认及公开确认。不会因收到非验证码回执就关闭浏览器；可恢复的提交／检查错误保留页面和独立错误说明，不将操作失败误判成账号失效。显示页面不重新授权提交，原有已接受或不确定请求仍只读核对。关闭 WebUI 面板后释放已返回结果的浏览器，待提交和验证码画面仍按既有流程保留；普通后台操作仍在完成后释放浏览器。

### 控件定位与现场截图

官网滚动或列表重新渲染后，原元素与坐标可能失效。点击前会等待布局完成、重新查找目标控件、确认点击位置实际命中目标，再执行一次真实点击；楼层回复的编辑器限定在已验证的父楼内。准备失败时保留现场，不把控件定位失败当成账号登录失效。

每次官网发布保存回复入口点击后、已填好、提交前、点击提交后和结果返回的实际截图；失败时保存失败画面与具体步骤、控件命中情况、页面文字和网络错误。WebUI 的「本次官网现场截图」按请求查看，诊断内部码与正文差异放在可展开的技术详情中，主提示显示人能理解的具体故障。截图仅存在账号私有目录，经主人鉴权读取，不包含 Cookie 或请求头；保留最近12个请求的现场，旧现场按请求清理。

2026-11-16 的一次主人授权实际操作：原文回复到主题 `11198809317` 的第44楼（父PID `154145808731`），官网接受一次提交，生成子回复 `154145902108`，随后非登录读取确认完整正文公开可见。本次证明这条楼中楼路径完成，不将单次成功表述为长期稳定。

### 主题正文与子回复的识别

主题正文在读取接口中也是第1楼，但官网将其放在主题区域，没有普通楼层的行内回复按钮。读取结果的第1楼 `replyTarget` 因此指向主题；历史目标仍可按实际读到的 `parentPost.floor=1` 使用主题回复框，公开回查也使用同一盖楼路径。普通楼层及子回复仍走原有楼中楼，不按作者、文字或猜测的 ID 改变目标。

官网子回复的 `#(reply, portrait, name)` 标记会在 portrait 后附加 `?t=时间戳`。这是公开头像缓存参数；核对时只去掉该标记内部的数字时间戳，仍严格核对头像身份、收件人名字、父子回复 ID 及整段正文，不放宽普通链接或正文检查。

展开回复框时，程序先定位、滚动并检查可见控件，再在同一次页面操作中激活该普通 DOM 回复按钮，避免分开的鼠标移动与点击遇到布局变化。已展开的编辑器不重复打开；尚未展开时仅重试打开编辑器，发布仍未授权。填写、提交仍通过官网编辑器和原生发布按钮，发布请求不会因打开编辑器重试而重复发送。最终没能展开时报告具体的编辑器故障并保留截图，不能把上一次点击信息当作这次操作的现场。
