# 验证码、实时画面与排错

[贴吧目录](README.md) · [发布状态](publishing.md) · [活动记录](../activity-diagnostics.md)

## 查看当前被哪一步挡住

WebUI 复用既有状态刷新，展示最新发言／申请的请求 ID、参数、阶段和实际回执。本地参数校验或准备错误即使没有进入发布出站表，也会显示；不会拿它伪装成百度拒绝。

官网实际要求验证时，会自动打开当前请求对应的官方画面。用户可以点击、拖动或正常输入完成验证。画面跟随当前请求刷新；新请求替换时清掉旧画面，返回的截图也核对请求 ID。收起面板保留实际等待验证的窗口。

不是所有错误都有验证码界面：参数错、找不到目标编辑器、网络失败等应显示真实原因。不能为了排错制造一个验证码页面。

## 不同问题分别处理

| 现象 | 如何理解／处理 |
| --- | --- |
| `TIEBA_*INPUT*` 等参数反馈 | 查看字段及原因；请求可能尚未发出，按实际读到的 ID 重新组织参数 |
| 父楼或子回复核对失败 | 核对父子 ID、贴吧、主题与子回复页码，见 [读取说明](reading.md) |
| 官网编辑器或目标不可见 | 查看准备阶段；当前页面结构可能变化，不视为发布成功 |
| 真实安全验证 | 在当前官方画面正常完成，检查该请求的真实结果 |
| 已接受、有 PID | 先只读检查公开可见性，不把“没立即看到”当作补发许可 |
| 超时或未知回执 | 保留未知状态与记录，只读核对，不能盲目提交第二次 |
| 登录失效 | 在“贴吧账号”重新登录并确认当前身份 |

已登录不意味着每次发言都免验证；一次人工验证或成功发布也不能证明长期稳定。项目不解验证码、不复制验证凭据、不伪造设备或轮换代理。

## 历史与当前状态

没有跨请求的“待人工验证”发布锁。旧请求的验证码只属于旧请求，新独立请求仍走当前真实流程。一个 Profile 的并发互斥是浏览器资源管理，不是对模型新请求伪造平台拒绝。

程序重启后保留意图与回执，浏览器进程本身不会被当成仍存活。恢复操作前区分已接受、明确拒绝和未知，不把重启变成自动重发。

完整模型输入、原生调用配对、错误和用量在私有活动记录查看。账号资料、Cookie、截图与详细真实发言不公开上传；公开文档只说明实现。
