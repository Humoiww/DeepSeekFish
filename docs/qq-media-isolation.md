# QQ 图片处理的内存与卡死恢复

2026-11-09 的现场记录：Codex 已成功生成 1024×1536、2183132 字节的 PNG（图库 ID `generated-f925f73c-c4e7-49b0-ad38-f2fba23c4d95`）。DeepSeek 随后选择 `send_image`，但请求停在 QQ 上传前的 `deliveryImage` 本地转换，尚无 `qq-image-upload` 记录或发送指纹。消息回合一直为 running。

服务的 memory.high 是 256 MiB，memory.max 是 384 MiB；现场 memory.current 约 265 MiB，high 事件超过 1900 万次，内存压力 full 约 80%。libuv/libvips 工作线程停在 `mem_cgroup_handle_over_high`。主机另有约 2.4 GiB 可用内存。QQ/Web/Native QQ 进程均未退出，账号与人民币额度正常。

同一 QQ 进程中还保留着无法结束的原生图片操作，自主探索的持久租约过期后，其进程内 active 对象仍未释放，新唤醒任务因此迟迟无法开始。单纯显示 WebSocket 已连上不足以代表聊天队列正常。

修复：

- 发送生成图时直接上传图库原字节，保留 PNG/GIF；不在聊天主进程内压缩、重绘、改格式或解码。文件发送继续使用原字节。
- 静图解析及动图抽样改成一次性 Node 子进程，复用原来的 sharp 解码和帧选择。原生内存随进程退出释放；聊天进程不再加载此解码器。
- 子进程并发为 1，排队输入总量至多 64 MiB、至多 4 个任务；单图原有 32 MiB、24M 像素和 500 帧边界不变。
- 子进程自行在 11 秒超时退出；父进程的 12 秒期限会强制终止并等待回收。失败会返回明确的 `QQ_MEDIA_DECODE_TIMEOUT`，后续队列仍可继续。子进程退出或管道断开不会被当成成功。
- 不把 API 密钥或登录环境传入解码子进程。子进程只接收二进制图片，返回有长度边界的元数据和 PNG 样本，不接收模型指定的命令或宿主路径。

不修改人格、香港时间安排、共享预算、QQ 登录、主机资源配置或服务权限。

已卡在旧原生代码里的进程需要重启才能释放；部署/重启按现有明确确认流程处理。旧记录的 unconfirmed 状态继续遵守禁止盲目重投的规则；只有确认在真实上传之前卡住的请求才能作为定向恢复处理，不能把所有未知发送都改为失败或重发。
